# تقرير المشروع النهائي — نظام وكيل محادثة لخدمة العملاء (متجر النخبة)

**المرجع المعماري:** `docs/ADR.md`
**الحالة:** جميع مراحل ADR الثماني (0–7) مكتملة ومنفَّذة ومتحقَّق منها فعلياً.
**التاريخ:** 2026-09-11

---

## 1. ملخص تنفيذي

بُني وكيل محادثة عربي لخدمة عملاء متجر إلكتروني وهمي («متجر النخبة»)، يستقبل رسائل العملاء
**باللهجة العامية اليمنية/الخليجية**، ويصنّف نيتها عبر **نموذج RNN مدرَّب محلياً (BiLSTM)**،
ويستخرج منها رقم الطلب واسم المنتج، ويستعلم من **قاعدة بيانات SQLite حقيقية** عبر أدوات، ثم
يولّد رداً عبر **LLM** ضمن **LangGraph** مع ذاكرة دائمة، ويُعرض كل ذلك في **واجهة React** متصلة
بـ **backend Flask**.

## 2. تحقيق المتطلبات الأكاديمية (ADR قسم 0.2)

| المتطلب | كيف تحقّق | الدليل |
|---|---|---|
| 1) تدريب نموذج RNN لتصنيف النية | Embedding → BiLSTM → Dense → Softmax (4 فئات)، مع مقارنة 3 معماريات | `docs/ADR.md` ق6، `training/reports/model_comparison.md` |
| 2) تحميل ومعالجة داتا سيت غير نظيفة | 4000 رسالة عامية بأخطاء إملائية وتنوع أسلوبي، مع تطبيع وتحقّق جودة | `training/reports/dataset_summary.md` |
| 3) استخراج معلومات من النص الحر | `agent/extractor.py`: regex لأرقام الطلبات + مطابقة منتجات على مستوى الكلمات | `backend/tests/test_extractor.py` |
| 4) AI Agent باستخدام LangGraph | 6 عقد + حواف شرطية + `SqliteSaver` + أدوات | `backend/agent/graph.py`، `backend/tests/test_graph.py` |
| 5) System Prompt و Context Engineering | برومبت نظام مُهندَس + سياق يُبنى ديناميكياً من مخرجات العقد | `backend/agent/prompts.py`، ADR ق9 |

## 3. المعمار النهائي

```
React (ChatWindow)  ──HTTP JSON──►  Flask (app.py)  ──►  SQLite (support.db)
                                        │                  - chat_messages (سجل دائم)
                                        ▼                  - tickets / orders / policies / products / customers
                              LangGraph (agent/graph.py)
                              ├─ classify_message   → نموذج RNN
                              ├─ extract_info       → regex + مطابقة
                              ├─ fetch_order_status → check_order_status
                              ├─ fetch_policy       → check_policy (return + refund)
                              ├─ escalate_ticket    → create_ticket
                              └─ craft_response     → LLM + سياق مبني ديناميكياً
                                        │
                              SqliteSaver (agent_memory.db)  ← ذاكرة الوكيل الدائمة
```

**فصل مقصود (ADR ق1.1):** `chat_messages` (سجل العميل الدائم للعرض) منفصل تماماً عن
`SqliteSaver` (ذاكرة تفكير الوكيل)، ويُربطان بنفس `session_id` = `thread_id`.

## 5. أرقام المشروع

- **النموذج:** BiLSTM (Embedding 128 → BiLSTM 64 → Dense 64 → Dense 4)، حجم مفردات 8056، `max_len=40`.
- **مقارنة النماذج (Test):** BiLSTM **0.9450 / 0.9449** ← المعتمد · BiGRU 0.9433 / 0.9432 · Stacked BiLSTM 0.9183 / 0.9185.
- **الداتا سيت:** 4000 صف · 4 فئات متوازنة (25% لكل فئة) · تكرار 0.90% · متوسط 26.8 كلمة.
- **قاعدة البيانات:** 6 عملاء · 15 منتجاً · 15 طلباً (1001–1015 تغطي الحالات الأربع) · 3 سياسات.
- **الاختبارات:** **71/71** اختبار وحدة + **10/10** سيناريوهات E2E.
- **واجهات HTTP:** `POST /api/chat` · `GET /api/history/<session_id>` · `GET /health`، وأخطاء موحّدة بـ 400/500/502.

## 6. أهم القرارات الهندسية (تفصيلها في `PROGRESS.md`)

1. **بيئة Python 3.12** بدل 3.14 (لا حزم TensorFlow لـ 3.14).
2. **`model.keras` + `config.json`** هي صيغة الموديل المعتمدة (بدل `.h5`)، وحُدِّث ADR قسم 2/3/6.
3. **قائمة المنتجات:** قائمة النوتبوك (15 منتجاً) ألغت قرار Phase 0 (12 منتجاً) لاتساقها مع الداتا سيت.
4. **`SqliteSaver` بالمُنشئ** لا `from_conn_string` (تغيّر واجهة المكتبة)، وحُدِّث ADR 8.3.
5. **استهلاك الذاكرة:** الدورات اللاحقة تمرّر حقلي الدورة فقط، و`order_id` «ملتصق»، وتُصفَّر الحقول لكل دورة.
6. **حظر اختلاق الأرقام/المدد** وحظر **تنسيق Markdown** في `SYSTEM_PROMPT`.
7. **حلّ المسارات** في `config.py` نسبةً لموقع الملف لا لمجلد التشغيل.
8. **سباق تحميل السجل** في الواجهة أُصلح بعدم استبدال رسائل المستخدم.

## 7. المخاطر والقيود المعروفة (معلنة بصراحة)

1. **سوء تصنيف الرسائل المختلطة** (مثل «شكراً، وكم مدة الإرجاع؟» تُصنَّف `other`). حارس الاختلاق يمنع الأثر الأخطر (ذكر أرقام غير مسنودة)، لكن الوكيل قد لا يجيب عن المدة. **بند قياس مستقبلي.**
2. ~~**ادّعاء إجراء لم يحدث**~~ — **أُصلح ومُتحقَّق منه**: وُسِّعت قاعدة عدم الاختراع لتشمل الأفعال (لا ادّعاء لتسجيل/حفظ/رفع إلا بتأكيد `created=true`)، وأُعيدت صياغة بند الشكوى المُتناقض. إعادة تشغيل السيناريو 10: صفر ادّعاءات، والرد صار يعرض المتابعة.
3. ~~**انحراف لهجي («نورت»)**~~ — **أُصلح ومُتحقَّق منه**: أُضيفت الكلمة إلى قائمة المنع (البرومبت + ADR + الفحص الآلي)، وإعادة تشغيل السيناريو 5 أعطت صفر كلمات ممنوعة، مع فحص ذاتي يثبت أن المُكتشِف يعمل.
4. **عدم تطابق إصدار scikit-learn** بين Colab (1.6.1) والمحلي (1.9.1) عند تحميل `label_encoder.pkl` — تحذير فقط، بلا أثر ظاهر.
5. **الأدوات لا تتحقق من ملكية الطلب للعميل** (متوافق مع ADR).
6. **قيود الاستخراج:** أي رقم 3–6 خانات بعد كلمة مثل «رقم» يُعتبر رقم طلب؛ والتطبيع يطوي الرموز المكررة ثلاثاً حتى في الأرقام.
7. **CRA مهجور** (يعمل حالياً على Node 24 بلا مشاكل).
8. **ثبات اللهجة عبر جلسات كثيرة** لم يُقس بعد إحصائياً (الفحص الآلي قائم على قائمة كلمات، لا على مصنّف لهجة).
