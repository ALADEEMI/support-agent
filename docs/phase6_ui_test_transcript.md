## كيف نُفِّذ الاختبار

1. تشغيل الـ backend (`python app.py`) والـ frontend (`npm start`).
2. فتح الصفحة في Chrome، ثم **كتابة الرسائل والإرسال من داخل الواجهة نفسها** (لا عبر API مباشرة).
3. بعد كل رسالة: انتظار ظهور فقاعة العميل وفقاعة الوكيل.
4. إعادة تحميل الصفحة (`Page.reload`) والتأكد أن السجل يُعاد بناؤه من `GET /api/history/<session_id>`.

## خطأ حقيقي اكتُشف وأُصلح أثناء هذا الاختبار

ظهرت في أول تشغيل أن **فقاعة العميل تختفي** رغم وصول الرسالة للـ backend (مؤكَّد من `chat_messages`).
أثبت `MutationObserver` على حاوية الرسائل التسلسل:

```
init:  ["الحالة الفارغة"]
mut:   ["فقاعة العميل", "جاري الكتابة..."]   ← أُضيفت فقاعة العميل
mut:   ["جاري الكتابة..."]                    ← حُذفت فقاعة العميل!
mut:   ["ردّ الوكيل"]                         ← أُضيف الرد
```

**السبب:** سباق زمني — طلب تحميل السجل عند أول تحميل للصفحة تأخّر (بدء بارد)، فوصلت نتيجته
**الفارغة** بعد أن أضاف المستخدم رسالته، فمحتها عبر `setMessages(history)`.

**الإصلاح** في `ChatWindow.jsx`: لا يُستبدل السجل إلا إذا كانت قائمة الرسائل ما زالت فارغة
(`setMessages(previous => previous.length === 0 ? history : previous)`)، مع علم `cancelled`
لتفادي تحديث حالة مكوّن أُزيل. بعد الإصلاح نجح الاختبار بالكامل (4 رسائل ← 8 فقاعات، وإعادة التحميل ← 8).

**ملاحظة:** هذا الخلل يظهر بوضوح عند البدء البارد، لكنه سباق حقيقي قد يحدث في الإنتاج عند بطء
الشبكة أو قاعدة البيانات — أي أنه إصلاح صحيح وليس مجرد ترقيع لبيئة الاختبار.
